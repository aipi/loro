# ADR-0005 — `/loro-sync`: external meeting notes as brainstorming context

- **Status:** accepted (owner decision, 2026-07-29)
- **Context:** the owner attends meetings whose notes are generated by Gemini
  and saved to Google Drive — some in a personal "Meet Recordings" folder,
  others shared by a colleague (a third party's meeting). He wants to bring
  those notes into a Loro brainstorming as context, the same way a local
  meeting already becomes context, **without** reading, downloading or storing
  the transcript body — only confirming it *is* a Drive meeting note (by title
  and folder, or by being shared by someone else) and recording a reference
  (title, link, date).

## Decision

### §1 Command shape: `/loro-sync <fonte> <alvo>`

The command name is deliberately generic — `<fonte>` names the external
system (v1 implements only `drive`; a future `slack` or similar needs no
rename, only a new branch in the skill prompt). `<alvo>` is a `.md` note or a
brainstorming topic, relative to the acervo root — same addressing style as
`/loro-note`.

### §2 No OAuth in the Tauri app — ambient terminal-agent access

Rejected: embedding a Google OAuth desktop flow (client registration, token
storage, Keychain) directly into the Rust/Tauri app. This has no precedent in
the codebase and would be heavy, one-off engineering for a single source.

Instead, `/loro-sync` follows the same **ambient-credential model** already
established for the AI agent (ADR-0004 baseline, `config.rs`: "the app never
ships credentials"): the check against Drive runs inside the **terminal agent
already embedded in the app** (the same `claude` process that materializes
`/loro-note`, `/loro-context`, etc., via `.claude/commands/*.md`), which may
already carry its own connector access. The Loro binary itself never talks to
Google's API and never stores a token (BR-9). This also satisfies **BR-1**
(external calls are opt-in per invocation): the sync only runs when the user
explicitly triggers the command, never automatically.

**Operational dependency (not resolvable in code):** the embedded terminal
session must itself have the Google Drive connector configured/authenticated
for `/loro-sync drive` to do anything. Documented in the manual as a
prerequisite, not something the app can verify or provision.

### §3 Validation heuristic, run by the agent — never by Rust

A candidate is accepted only if its title matches `... - Anotações do
Gemini` **and** (its parent folder is "Meet Recordings" on the current
account **or** its owner is someone else — a meeting shared by a colleague).
This heuristic lives entirely in the skill prompt (`templates.rs`,
`loro_sync_skill`), executed by the terminal agent against Drive metadata —
Rust never touches the Drive API. The agent must always present candidates
for explicit user confirmation before attaching; silent attachment is
forbidden by the skill's rigor rules.

Validated against a real shared meeting during implementation
("TP - BARAD DUR - ... - Anotações do Gemini", owned by a colleague): the
Drive API returns **no `parentId` at all** for a document you don't own —
confirming the "OR owner is someone else" branch is load-bearing, not
redundant, for the most common external-meeting case.

**First real run still missed the shared meeting** — the skill's search step
was under-specified and a terminal agent could (and did) narrow the search to
documents owned by the current user, which silently excludes exactly the
case this feature exists for. Fixed by making the prompt explicit: the
search **must never filter by owner**, and if the initial title search comes
up empty the agent must retry with a broader keyword before reporting
nothing found — this is a prompt-engineering fix, not a Rust/heuristic
change (§3's acceptance rule was already correct; the search that fed it was
not).

**Escape hatch — `[busca-ou-link]` optional third argument:**
`/loro-sync drive <alvo> [busca-ou-link]`. When given, it is either a title
keyword (narrows the search — useful for a distinctive meeting name) or a
direct `https://docs.google.com/...`/`https://drive.google.com/...` link
(skips search entirely, going straight to metadata confirmation). This gives
the user a manual override whenever the agent's own search still fails to
surface the right document, without weakening §4 (still title/link/date
only, never the body).

### §4 New ref kind: `tipo: drive`, `caminho: <url>` — link only, never content

The note's front-matter `refs:` gains an entry shaped like any other ref
(`id`, `tipo`, `caminho`), but `caminho` is the full `https://` document link
instead of an `acervo://...` path. This is the **only** thing recorded — never
the document body (**BR-8**: no transcript/PII in the acervo). The skill edits
the target note's `.md` file directly (Read/Edit), the same mechanism
`/loro-note` already uses — `brain_add_ref` (the Tauri IPC command) is not
reachable from a terminal/CLI session, only from the webview.

Two small, pre-existing Rust functions assumed every `caminho` was either
`acervo://...` or a local relative path and would have corrupted a URL:
- `anchor_path` (`acervo.rs`) now leaves `http://`/`https://` values untouched
  instead of prefixing `acervo://`.
- `resolve_ref` (`acervo.rs`) now short-circuits `http(s)` refs to
  `RefResolution { tipo: "link", exists: true }` without touching the
  filesystem.
- A new command, `brain_open_link`, opens a `tipo: link` ref in the OS default
  browser — restricted to `http(s)` schemes only (`is_openable_link`), never
  passed to a shell. `brain_open_external` was not reused: it is guarded to
  paths *inside* the acervo root and cannot serve an external URL.

### §5 Deferred / out of scope

- Other sources named by `<fonte>` (Slack, etc.) — no code, only the
  extensible command shape.
- Any automatic/background sync — every run is a manual, explicit invocation.
- Reading or excerpting the Drive document's body for the report/summary — a
  future ADR would be needed to revisit BR-8 if that is ever wanted.

## Consequences

- `templates.rs`: new `loro_sync_skill(lang)` (pt/en), registered in
  `lib.rs`'s three skill-materialization sites (`ensure_acervo_structure`,
  the migration block, `ensure_meeting_skills`) alongside the other five
  skills — create-if-absent, never overwrites user edits.
- `acervo.rs`: `anchor_path`/`resolve_ref` gain an external-link branch;
  new `brain_open_link` command.
- `app.js`/`brainstorm.js`: a "sincronizar reunião" button next to "nova
  nota" opens a modal for an optional search-keyword-or-link, then injects
  `/loro-sync drive <tema> [busca-ou-link]` into the embedded terminal
  (`syncCmd`, `promptSyncDrive`); the ref-click dispatcher opens
  `tipo: "link"` refs via `brain_open_link`.
- Tests assert: URL-safe `anchor_path`/`resolve_ref`, ref round-trip with
  `tipo: drive`, `is_openable_link` scheme allowlist, and the new skill
  passes the shared "no unstated premises / fast scanning" rigor check.
