# ADR-0043 — The chat speaks the terminal's language: commands, questions, permissions

- **Status:** accepted, implemented 2026-11-23 (owner's request).
- **Amends:** ADR-0021 §1 (the turn is no longer one-way `-p` with the prompt as plain stdin text) and §2 (a permission is asked *during* the turn when the mode asks at all; the after-the-fact amber block stays for what is still refused); ADR-0041 §11 (the «/» list is the CLI's own, and its sentence «no CLI built-ins are listed: the ones that exist … do nothing in `-p` mode» was measured false — see below).
- **Keeps:** BR-1/BR-9 — still the acervo's own agent CLI, local, under the person's account; Loro stores no credential and calls no API. ADR-0042 — the permission mode and the deny list are unchanged and still decide what may run.

## Context

The owner, 2026-11-23: «quero que todos os comandos que funcionam no claude terminal funcionem aqui também, e que as interações do terminal também funcionem — todos os comandos do claude e seleção de opções, etc. — sem perder a usabilidade». Measured against the installed CLI (2.1.329) the same day, the chat (main panel and bubble) had three gaps:

1. **Commands.** The main chat wrapped every message in `/loro-ask`, so `/context` became a question *about* «/context». The bubble sent it raw, but its «/» list came from the skill files on disk, with no built-ins — ADR-0041 §11 assumed none work in `-p`. Measured: `initialize` lists **108** commands usable in print mode (`compact`, `context`, `model`, `clear`, `cost`… plus every skill), and `init` names the terminal-only ones separately (`doctor`, `color`, `focus`, `reload-plugins`; `/login` is in neither list). And a built-in's reply arrives as ONE `assistant` message with `model: "<synthetic>"` and no text deltas — read only from deltas, as the chat did, it was a blank answer.
2. **Questions with options.** In plain `-p`, AskUserQuestion is **not offered to the model** (it replied «the tool isn't available»), with or without `--tools`. It appears only with `--permission-prompt-tool stdio`.
3. **Permissions.** In plain `-p` a tool that needs permission is denied; the chat showed the amber block afterwards (ADR-0021 §2) and the person had to retry.

## Decision

1. **The chat's turn is two-way stream-json** (`claude_chat_args`): the ADR-0021 arguments plus `--input-format stream-json --permission-prompt-tool stdio`. The prompt goes in as one `{"type":"user",…}` line and **stdin stays open** until the turn's `result` line, because it is the channel the answers travel on; closing it is what ends the turn. Still one process per turn and `--resume` between turns (ADR-0021 §1).
2. **Loop cycles keep the one-way `claude_args`.** Nobody watches a cycle: a question routed to a host would wait forever. A test pins it (`adr0043_a_cycle_never_waits_for_a_person`).
3. **What the CLI asks becomes a block in the conversation.** A `control_request` / `can_use_tool` is emitted as `{ch}-ask` `{requestId, kind: "question"|"permission", tool, input, description, canRemember}`; the input is parked by request id, because the answer must echo it back. The person answers with **`chat_answer`** `{channel, requestId, allow, answers?, remember?, message?}`:
   - a question → `allow` + `updatedInput = {questions, answers: {question → label | [labels] | own text}}`;
   - a permission → **Permitir** (`allow`, input unchanged), **Permitir sempre nesta conversa** (`allow` + `updatedPermissions` = the CLI's own `permission_suggestions` — measured: the second write of the same turn was not asked again), **Negar** (`deny` + `message`, optionally what to do instead, which the model reads).
   Any other control request is **answered with an error, never ignored**: the CLI blocks until each one is answered. A question still open when the turn ends or is stopped is disabled (`err.chat_question_expired` if answered late).
4. **Usability, the terminal's keys:** options are buttons with their description; **1–9** pick, a single one-choice question answers on click (Enter on the terminal's list), a free-text field replaces the options («outra resposta…»), **Pular** skips. Once answered, only the choice remains visible — as the terminal leaves the answered line.
5. **«/» is the CLI's own list** (`agent_commands`): one `initialize` control request in the acervo dir, no turn started (no tokens), ~1 s measured, cached 5 min per agent+project, run off the main thread (ADR-0022 §28). Another agent, or a probe that fails within 12 s, falls back to `skills_list` (ADR-0041 §11). Both chats use it, with the same popover (`agentask.js`: ↑/↓, Tab/Enter, Esc, the argument hint after the name).
6. **Where a «/x» goes** (`LoroAgentAsk.classify`): listed → sent to the CLI **unchanged** (the main chat no longer wraps it in `/loro-ask`); not listed → **terminal-only** (`/login` is interactive — it opens the browser to sign in — and print mode does not have it): the main window opens its embedded terminal, which already runs the agent's TUI (ADR-0005), and types the command INTO it, the way a skill is run (`termRunAgent`) — from the bubble via `bubble-cmd` `terminal-command`, since the main window owns the terminal (ADR-0041). The first version typed a shell line (`claude '/login'`) there, i.e. into Claude's own prompt (owner's screenshot, 2026-11-23). And Enter is a separate `"\r"`: measured over a pty, `"/cost\n"` in one write stays parked in the prompt, `"/cost"` then `"\r"` runs — this also fixed skills run in the terminal. With no list yet, nothing is guessed: the message goes to the CLI.
6a. **Interactive commands go to the terminal too** (owner, same day: «faz sentido comandos interativos abrir o terminal, como foi feito no login»). Some commands ARE listed by `initialize` but open a picker in the terminal; sent bare in the chat's mode they only print text (measured): `/config` and `/advisor` → «Usage: …», `/mcp` → «Use `/mcp` in the terminal for details», `/output-style` → a list, `/color` → a random colour. Bare, they go to the terminal; with an argument they run in the chat. `/fast` («not available in the Agent SDK») and `/focus` («isn't available here yet») always go to the terminal. The list is in `agentask.js` with these measurements.
6b. **`/model` and `/effort` are the chat's own control.** Measured: `/model sonnet` in the chat answered «Set model to Sonnet 5.5 for this session only», and the next turn ran on the model Loro passes with `--model` — it looked done and was not. In the terminal, `/model` changes the model of the conversation you type it in; the chat does the same: `/model opus` / `/effort high` set the chat's model/effort (the bubble's via `bubble-cmd` `chat-model` / `chat-effort`), and bare they open the chat's picker. Never the terminal's: that is another session.
7. **A built-in's reply is read from the synthetic message** (`synthetic_text`): only `model == "<synthetic>"`, so a model reply — already streamed as deltas — is never printed twice.
8. **One module, two windows:** `src/agentask.js` (pure: `classify`, `answersFrom`, `complete`, `summarize`, `slashQuery`, `slashItems`; DOM: `renderAsk`, `attachSlash`) is loaded by `index.html` and `bubble.html`; the bubble's former copies in `bubble-core.js` were removed. The protocol is `src-tauri/src/chat_protocol.rs`, pure; `chat.rs` owns the process.

## Consequences

- In «Livre» (ADR-0042's default) the CLI never asks for permission, so only questions with options appear; in «Restrito» every gated action is asked in the conversation instead of failing the turn.
- The amber «faltou permissão» block remains for what is still refused without asking (a tool on the deny list).
- The evidence is repeatable: `cargo test --lib adr0043_live -- --ignored` runs the real CLI with the real argv and lines (a question answered «Pear» comes back as «Pear»; the list has `compact`/`context` and not `login`). `tools/smoke-ui.js` and `tools/smoke-bubble.js` measure both blocks in the DOM.
- Not done: the terminal-only list is inferred as «not in `initialize`», not read from `init.terminal_slash_commands` (that field only arrives once a turn starts).
